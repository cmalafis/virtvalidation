# VirtValidate — Codebase Snapshot

> Generated 2026-05-02. Mirrors current `main`. Intended as a context
> document for AI assistants and onboarding engineers — read once,
> then trust the actual code on changes.

VirtValidate is an air-gapped appliance that validates VMs migrated
from VMware to OpenShift Virtualization. Pre-migration baselines are
captured via SSH, post-migration state is diffed, and a local LLM
reasons over the diff to produce structured findings. The same LLM
also generates dependency-ordered migration waves and reviews
proposed network designs.

- **Backend** — Python 3.12 + FastAPI + SQLAlchemy 2.0 + APScheduler
- **Frontend** — React 18 + Vite 6 + react-router-dom
- **LLM** — Pluggable backend (Ollama / KServe / vLLM placeholder)
- **DB** — PostgreSQL 16 (SQLite for tests)
- **SSH** — Paramiko, Ed25519 / RSA-3072 / ECDSA P-384 keys
- **Containers** — Podman + podman-compose for dev; Helm + Kustomize for OCP

**Test suite:** 316 tests (`pytest`), full pass on every recent commit.

## 5. Core Business Logic

### `core/ssh.py` — SSH Collection Engine

Talks to managed VMs via Paramiko. Polymorphic key loader accepts
Ed25519 / RSA / ECDSA. FIPS gate runs at connect time and rejects
non-approved key algorithms when `FIPS_MODE=true`. Output handling
strips UTF-16 LE/BE BOMs and CRLF (Windows PowerShell over OpenSSH).

**Key public:**
- `SSHCollector.__init__(key_path, port, timeout, command_timeout, *, host_key_policy, known_hosts_path)`
- `SSHCollector.collect(host, username) -> dict` (the canonical baseline shape)
- `load_private_key(path) -> paramiko.PKey` (auto-detect type)
- `SSHCollectionError(kind={generic,host_key_mismatch,host_key_unknown})`

**Detection flow (in `collect`):**
1. POSIX probe: `cat /etc/os-release` + `uname -r` + `uname -m`.
2. Fall through to Windows probe: `Get-CimInstance Win32_OperatingSystem | ConvertTo-Json`.
3. Build `OSProfile`, dispatch `CommandSet`.
4. Linux path: `_collect_services` / `_collect_network` / `_collect_ports` / `_collect_mounts` / `_collect_cron` (line-based parsing).
5. Windows path: `_collect_windows*` collectors that parse JSON and **normalize to the same shape** (services/ports/mounts/cron/network) plus extras (`hotfixes`, `ad_membership`).

**Host-key policy:** `auto_accept` (TOFU writes to persistent `known_hosts` next to the private key) or `strict` (rejects unknown). Mismatches raise `host_key_mismatch` and audit-log loudly.

### `core/os_profile.py` + `core/commands.py`

- `OSProfile` dataclass — distro, distro_family (`rhel-like` | `debian-like` | `windows` | `unknown`), major/minor version, kernel, arch, is_systemd, pretty_name, detection_confidence (high/medium/low).
- `detect()` — POSIX `/etc/os-release` parser.
- `detect_windows()` — Win32_OperatingSystem JSON parser (build → product mapping for 17763=2019, 20348=2022, 26100=2025).
- `CommandSet` — frozen dataclass of every shell command the collector runs. Linux fields are POSIX commands; Windows-only optional fields (`windows_hotfixes`, `windows_ad_membership`, etc.) ride alongside.
- `command_set_for(profile)` — single dispatch point: `windows` → PowerShell + ConvertTo-Json bundle; `rhel-like` → RHEL 7 (legacy ss/yum) or modern (`ss -tulnH`/dnf); `debian-like` → apt; otherwise modern-Linux defaults.

### `core/llm/` — Pluggable Inference Backend

```
core/llm/
├── base.py              # LLMBackend ABC + LLMBackendError + chat_sync bridge
├── ollama_backend.py    # OllamaBackend — default for standalone
├── kserve_backend.py    # KServeBackend — RHOAI / OpenShift inference
├── vllm_backend.py      # VLLMBackend — placeholder (raises NotImplementedError)
├── factory.py           # get_llm_backend(settings) — dispatch + cache
├── client.py            # LLMClient (validation domain) + diff helpers + SYSTEM_PROMPT
└── __init__.py          # Re-exports for back-compat with `from app.core.llm import …`
```

**`LLMBackend` ABC:**
- `async def chat(messages, model, temperature, max_tokens) -> dict`
- `async def chat_stream(messages, ...) -> AsyncIterator[str]`
- `async def health_check() -> dict` (status / backend / model / endpoint / latency_ms / details)
- `def list_models() -> list[str]`
- Concrete `chat_sync` / `health_check_sync` bridges via `asyncio.run()` for sync callers (BackgroundTasks).

**`get_llm_backend(cfg)`** dispatches on `cfg.llm_backend_type`:
- `ollama` → `OllamaBackend(base_url, default_model, timeout=120)`
- `kserve` → `KServeBackend(endpoint, model_name, token, token_file, verify_ssl, timeout)` (OpenAI-compatible `/v1/chat/completions`)
- `vllm` → `VLLMBackend(endpoint, model_name)` placeholder

**`LLMClient` (validation orchestrator):**
- Domain logic — system prompt, verdict parser, diff engine.
- Calls `backend.chat_sync()` with platform-aware user prompt (Linux vs Windows terminology hint).

The planner (`MigrationPlanner`) and network reviewer
(`NetworkReviewer`) follow the same DI pattern — each takes a backend
in its constructor and defaults to `get_llm_backend()`.

### `core/planner.py` — Migration Wave Planning

`MigrationPlanner.plan(vm_profiles)` — single LLM call that groups
VMs into dependency-ordered waves applying these rules in order:

1. Application dependencies (stateful first, edge last).
2. Shared vSphere portgroups.
3. Shared vSphere datastores.
4. Risk profile per wave.

**Output schema** (validated by `_parse_plan`):

```json
{
  "summary": "...",
  "waves": [
    {"wave_number": 1, "vm_ids": [...], "rationale": "...", "estimated_risk": "low|medium|high"}
  ]
}
```

Strict validation rejects unknown vm_ids, duplicate vm_ids across
waves, and missing-from-any-wave vm_ids. This is the **Level 3**
slot in the future hierarchical planner; today it runs on the entire
set in one shot.

### `core/categorizer.py` — Level 1 Hierarchical Planning

Batches a vCenter's VMs into groups of 100 (max 200) and calls the
LLM once per batch to identify application / environment /
business_unit groupings.

**Public:**
- `categorize(db, *, source_vcenter_id, backend?, batch_size=100, progress_cb?) -> {groups_created, batches_processed, members_added, run_id}`
- `run_categorization_task(task_id, source_vcenter_id, *, batch_size)` — BackgroundTask entry point.
- `task_store` — in-memory, RLock-guarded, ephemeral progress registry.

Behaviors:
- Re-running drops prior groups for the same vCenter (idempotent).
- Hallucinated vm_ids dropped silently with a logger.warning.
- Concurrency = 1 today (Ollama is single-threaded). KServe-driven parallelism is a follow-up tagged `parallelize-categorizer`.

### `core/validation.py` — Post-Migration Validation

`run_validation` orchestrates: load baseline → SSH-collect current →
LLM diff/reason → persist `ValidationResult` → update VM status →
audit. The same task-store + BackgroundTask pattern as capture.

Verdict mapping:
- `pass` → `VMStatus.validated`
- `warn` → `VMStatus.validated`
- `fail` → `VMStatus.failed`

### `core/capture.py` — Baseline Capture

`collect_and_store(db, vm, *, actor, collector?)` — shared SSH+store
helper used by both the scheduler and the manual-trigger endpoint.
Audits `baseline.collected` plus `ssh.host_key_accepted` /
`ssh.host_key_mismatch` events.

`task_store` for ephemeral progress; `run_capture_task` is the
BackgroundTask body.

### `core/mtv.py` — MTV/Forklift YAML Generation

Renders multi-doc YAML containing `Plan`, `NetworkMap`, `StorageMap`
resources for a wave. Source/destination Provider names pulled from
settings. Used by `GET /api/plans/{id}/waves/{n}/mtv-yaml`.

### `core/baseline.py` — Profile Synthesis

`synthesize_profile(vm_id, snapshots)` aggregates multiple
`BaselineSnapshot` rows into one stable profile (services that appear
in every snapshot, ports always open, mounts consistent across
captures). The synthesized profile is what the LLM sees in
`baseline_profile` — the planner uses it for grouping signals.

### `core/audit.py` — Audit Logging

- `record_audit(db, *, action, actor, resource_type?, resource_id?, details?) -> AuditLog`
- `infer_action(method, path)` — middleware action inference via regex table.

The `_ACTIONS` table maps mutating HTTP method+path to canonical
`action` strings. Endpoints emitting rich custom audits set
`request.state.skip_audit_log = True` so middleware doesn't double-log.

### `core/fips.py` — FIPS 140-3 Compliance

- `is_os_fips_enabled()` — reads `/proc/sys/crypto/fips_enabled`.
- `is_fips_mode(cfg)` — reads `FIPS_MODE` env via Settings.
- `assess_ssh_key(type, bits)` — pure verdict logic against FIPS 186-5.
- `validate_ssh_key(...)` — raises `FIPSViolation` when fips_mode is on.
- `fips_status(cfg)` — configured + detected + per-operation report.
- `log_startup_warning()` — boot-time mismatch warning.

### `core/scheduler.py` — APScheduler

Starts/stops with the FastAPI lifespan. Recurring baseline capture
job; `next_run_time()` exposed via `/api/settings`. Schedule presets:
`twice_daily` (06:00 + 18:00 UTC), `once_daily`, `hourly`.

### `core/network_review.py` — Network Design Reviewer

`NetworkReviewer.analyze(*, source_summary, customer_notes,
proposed_yaml)` — LLM-powered gap analysis between VMware portgroups
and a proposed OCP-Virt design. Findings categorized as
`coverage_gap`, `config_mismatch`, `missing_resource`,
`positive_confirmation`.

### `core/reporter.py` — Wave Report PDF

`WaveReporter.generate(wave, validations) -> dict` — LLM-generated
exec summary + per-VM findings rollup. `render_pdf(report) -> bytes`
uses WeasyPrint (Pango/Cairo runtime, see Containerfile).

## 11. Open Questions / Pending Decisions

1. **Alembic migrations vs `create_all`** — the project has shipped
   substantial schema changes (vCenter sources, VMGroup, FIPS fields,
   Windows is_systemd false case, source_vcenter_id FK). Each
   schema change in production today requires a fresh DB volume.
   Adding Alembic before more schema churn is a worthwhile pause.

2. **Scope of Level 2/3 hierarchical planner** — Level 1 ships and is
   tested. Level 2 (strategy, single LLM call per program) and Level
   3 (per-campaign waves with full VM context) are designed but not
   built. Streaming UI via SSE is the prerequisite. Open question:
   ship L2/L3 after the next round of customer feedback or front-run
   based on the SCALE.md design?

3. **Frontend API client consolidation** — every component re-defines
   its own `fetchJSON` helper. Worth a shared client (`src/lib/api.js`)
   before adding more components, but the duplication isn't actively
   hurting today.

4. **Windows Server 2016 support** — explicitly excluded from the
   tested matrix because OpenSSH isn't built-in. Some federal
   customers still run 2016. The collector code already handles it
   if OpenSSH is installed manually; the question is whether to
   document the manual install path or refuse 2016 outright.

5. **vLLM backend implementation** — the placeholder raises
   `NotImplementedError` and was tagged for v1.0.0. KServe with vLLM
   predictor satisfies most "I want vLLM" customer questions today.
   Open question: ship a direct vLLM backend (no KServe wrapper) or
   keep deferring?

6. **PDF report formatting** — WeasyPrint works but is heavy
   (Pango/Cairo runtime in the backend container). Lighter
   alternatives (e.g. ReportLab + manual layout) could reduce image
   size by ~80MB. Trade-off is layout sophistication.

7. **Multi-tenancy / RBAC** — the appliance is single-tenant today.
   The data model can absorb multi-tenant scoping (every table
   already has timestamps + the audit trail), but the UI is
   single-context. Tagged for v1.0.0 GA milestone.
